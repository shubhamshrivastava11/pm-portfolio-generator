Technical Course — Architecture & Design Analysis

How Dwelliq is built
and why it's built that way

A deep-dive into the system design of an AI home styling advisor — written for intermediate engineers and technical PMs who can read code but want architectural reasoning, not just implementation details.

⚠ Design Assumptions (explicit)

  • Persistence: sessionStorage is a deliberate MVP constraint — no auth or database layer in scope.
  • Affiliate tracking: Production intent is a first-party /api/click redirect endpoint for logging clicks before forwarding to retailers.
  • Scale: Vercel hobby/pro deployment; hundreds of concurrent users; 200-SKU catalog stays in-bundle for now.

Stateless vs stateful. The recommendation engine is entirely stateless — given the same budget, style, and room inputs, it produces the same outputs every time. State lives in two places only: React's useState for the current session's budget totals and category selections, and sessionStorage for the five onboarding answers. Neither survives a tab close. This is an intentional MVP constraint: no database means no auth surface, no GDPR scope, and zero cold-start latency on the results page.

Edge vs origin. All page renders are SSR at the Vercel origin on first load; subsequent navigation is client-side via React's router. The only edge function is /api/click, which is lightweight enough to run at the edge (no DB call, just a log + redirect). The 200-SKU catalog ships inside the JS bundle — it's ~40 KB gzipped, a deliberate trade-off at this scale (see Tradeoffs §3).

Security boundary. The most important line in the diagram is the boundary around the browser. Affiliate partner IDs and any future API keys (retailer search APIs, analytics SDKs) must never cross into the client bundle. The /api/click handler owns the affiliate partner ID; the browser only ever calls /api/click?sku=sofa-001 — a safe, non-secret parameter.

Section 02

Data Flow

End-to-end from the first browser request to the user clicking "Buy" — 11 steps covering the happy path and the error path at each stage.

①
Initial page load Edge CDN

User navigates to dwelliq.app. Vercel serves the Next.js HTML shell from the CDN edge. The page is pre-rendered at build time (static generation) — no SSR work needed for the public homepage. Google Fonts and the JS bundle load in parallel.

Error path: CDN miss on first deploy → Vercel origin renders the page cold. First request in a new region may take ~300–500ms. Subsequent requests are cached at edge.
②
JS bundle hydration Client

React hydrates the static HTML. The catalog (catalog.ts) and recommendation engine (recommendations.ts) are imported as ES modules — both ship in the client bundle. No lazy-loading at this scale. Total bundle size target: <150 KB gzipped including Three.js for the hero animation.

③
Onboarding: budget input Client

User enters a room budget (e.g., $3,000). The component validates: must be a positive number, minimum $500 (below this, no meaningful 3-tier recommendation is possible). The value is stored in React state and persisted to sessionStorage under a namespaced key: dwelliq_onboarding_v1.

// Shape stored in sessionStorage
{
  "budget": 3000,
  "style": "warm-mid-century",
  "roomType": "living-room",
  "householdSize": "couple",
  "hasPets": false
}
Error path: User enters non-numeric or negative value → inline validation message, step does not advance. sessionStorage write failure (private browsing on iOS with storage disabled) → fall back to React state only; user loses progress on tab close, but the session still works.
④
Onboarding: style & room questions Client

Steps 2–5 collect style direction, room type, household size, and pet status. Each answer is appended to the sessionStorage object. No network requests are made during onboarding — it's a pure local state machine.

⑤
Budget allocation Client

On "Get Recommendations", the budget optimizer runs synchronously in the browser. It applies hardcoded design-industry ratios: sofa 35%, case goods 20%, textiles 15%, lighting 10%, accent 10%, rugs 10%. These ratios produce per-category budget caps used in the next step.

// Budget allocation output for $3,000
{
  "sofa":      { "cap": 1050, "flex": 1260 },
  "caseGoods": { "cap": 600,  "flex": 720  },
  "textiles":  { "cap": 450,  "flex": 540  },
  "lighting":  { "cap": 300,  "flex": 360  },
  "accent":    { "cap": 300,  "flex": 360  },
  "rugs":      { "cap": 300,  "flex": 360  }
}
⑥
Recommendation engine: filter + rank Client

For each category, recommendations.ts filters the catalog to products matching the chosen style tags and household suitability. It then ranks by price against the cap to select: Option A (highest-rated product ≤ cap), Option B (highest-rated product in cap×1.3), Option C (first product with retailer === "Local Boutique" or nearest price to cap). The engine runs synchronously — no async, no network. Typical execution time: <5ms.

Error path: No products match a style/category combination → engine falls back to removing the style filter and returning the top 3 by rating. This guarantees the results page always has content but means the style match may be loose — logged as a console warning in development.
⑦
Results page render Client

Results are rendered as a client-side navigation (no SSR — the output depends entirely on client-side state). The A/B/C grid is built from the engine output. The budget tracker in the header initializes to the sum of all Option A prices. Swapping to B or C updates the tracker in real time via React state.

⑧
User swaps item options Client

User selects Option B for the sofa. React updates selectedOptions state: { sofa: 'B', rug: 'A', ... }. The budget tracker recalculates synchronously. No server call. If the new total exceeds the original budget, the tracker renders a red warning — but the selection is not blocked (user can be flexible).

⑨
Affiliate click-out Client → Server

User clicks "Buy at Wayfair" on a sofa card. The link calls /api/click?sku=sofa-002&option=B — an internal Next.js Route Handler. It does not expose the affiliate partner ID to the browser.

// /api/click handler (server-side, runs at Vercel edge)
export async function GET(req: Request) {
  const { sku, option } = parseParams(req.url)
  const product = lookupSku(sku)          // in-memory catalog ref
  logClick({ sku, option, ts: Date.now() }) // append to log / analytics
  const affiliateUrl = buildAffiliateUrl(
    product.baseUrl,
    process.env.AFFILIATE_TAG          // secret — never in browser
  )
  return Response.redirect(affiliateUrl, 302)
}
Error path: Unknown SKU → 400 Bad Request, no redirect. Missing AFFILIATE_TAG env var → 500, log error, no redirect (better to fail closed than to redirect without tracking). Retailer site down → user sees retailer's error page; no retry from Dwelliq's side.
⑩
Retailer redirect External

Browser follows the 302 to the retailer's product page with Dwelliq's affiliate tag appended. The retailer's cookie sets the attribution window (typically 24h for Amazon, 7 days for others). Dwelliq earns a commission only if the user completes a purchase within that window.

⑪
Session persistence across navigation Client

If the user navigates back from the retailer and re-opens Dwelliq in the same tab, sessionStorage still holds the onboarding context and the selected options are restored from React state (since the tab never closed). Closing the tab ends the session — by design. A future "save my list" feature would require auth and a database write at this step.

Section 03

Design Tradeoffs

Six decisions where the alternative was genuinely tempting — and why the chosen path fits Dwelliq's current stage better.

① Client-side recommendation engine vs server-side API

✓ Chosen — Client-side (catalog.ts + recommendations.ts in bundle)

The full 200-SKU catalog and all filtering logic ships in the browser. Recommendations run in <5ms with zero network latency. No API to secure, no cold starts, no rate limits, no cost per recommendation call.

× Rejected — Server API with database catalog

A /api/recommend endpoint backed by Postgres or a vector DB would enable personalization, A/B testing of recommendations, and a catalog too large for the bundle. Adds 100–300ms latency and significant infrastructure complexity for an MVP.

Impact: Bundle is ~40 KB larger (catalog payload). Acceptable at this scale. Hard limit: if the catalog grows past ~2,000 SKUs, the bundle approach breaks down and a server API becomes necessary. Design for that migration now by keeping the catalog import behind a single module boundary.

② sessionStorage vs user accounts for state persistence

✓ Chosen — sessionStorage (ephemeral, zero-friction)

No sign-up, no email capture, no GDPR consent flow. Users get the full product in <2 minutes. Affiliate revenue can be earned from completely anonymous sessions. Privacy by design: Dwelliq stores nothing about users server-side.

× Rejected — Auth + saved lists (Supabase / Clerk)

Saves recommendation lists across devices, enables email follow-up, unlocks retention data. But adds a sign-up barrier that will kill conversion for the majority of casual users at the MVP stage.

Impact: Users lose their list when they close the tab. Retention is zero by design. This is acceptable for v1 because the funnel ends at an affiliate click-out — re-engagement is the retailer's problem, not Dwelliq's. Add auth at v2 when retention data shows users actively want to return.

③ Static in-bundle catalog vs live product API

✓ Chosen — 200 curated SKUs in catalog.ts

Every product is manually curated for quality, style accuracy, and availability. Prices are approximate (updated on deploy). No scraping, no API costs, no risk of showing out-of-stock items in real time.

× Rejected — Live retailer product APIs (Wayfair DSv2, Amazon PA-API)

Real prices, live stock status, larger catalog. But Amazon PA-API requires a qualifying affiliate account ($10/day in commissions), has strict TOS about caching, and adds complexity around API key management and rate limiting from the browser.

Impact: Prices may be stale by deploy cycle. Mitigate by adding a "prices may vary" disclaimer on product cards and linking directly to the retailer page where the canonical price lives. Plan to move to live API when affiliate account qualifies.

④ First-party /api/click redirect vs direct affiliate links

✓ Chosen — /api/click server-side redirect

Affiliate partner IDs live in server environment variables. Click events are logged server-side (sku, option, timestamp). The client never sees the partner ID, preventing URL scraping and protecting revenue integrity.

× Rejected — Direct affiliate URLs in the client bundle

Simpler to implement — just render the full affiliate URL as an <a href>. But the affiliate partner tag is exposed in the HTML source, where scrapers or competitors can harvest it. Worse, if the partner ID is rotated, every deployed HTML file is stale.

Security impact: The /api/click pattern is the correct production pattern for any affiliate product. Partner ID rotation requires one env var change and a redeploy — not a catalog update. The mild cost: one extra HTTP request per click (fast, but adds ~50ms if the edge function cold-starts).

⑤ Tailwind v4 CSS-first config vs Tailwind v3 JS config

✓ Chosen — Tailwind v4 with @theme inline in globals.css

Design tokens live in CSS, not a JS config file. The theme is co-located with the global styles, making it easier for designers working in CSS to adjust tokens without touching JS config. Faster HMR on token changes.

× Rejected — Tailwind v3 with tailwind.config.js

More ecosystem documentation, wider tooling support, stable IntelliSense across all editors. v4 is still relatively new and some third-party Tailwind plugins have not migrated to the v4 plugin API.

Complexity note: v4 is a breaking change from v3 — the config format, plugin API, and some utility names differ. Anyone joining the project who knows v3 deeply will have a learning curve. Document the config format explicitly in CLAUDE.md or README.

⑥ Next.js App Router vs Pages Router

✓ Chosen — App Router (Next.js 13+)

Route handlers (/api/click) and server components live in the same app/ directory. React Server Components allow the page shell to render without shipping the catalog to the server-render pass. Layouts are co-located with routes.

× Rejected — Pages Router

More stable, wider community reference material, simpler mental model for teams new to Next.js. App Router is still the more complex mental model — especially the "use client" / "use server" boundary, which is non-obvious and a common source of bugs.

Pitfall: The catalog and recommendation engine are imported in client components ("use client"). Any file that imports from them transitively becomes a client component. Keep catalog.ts and recommendations.ts free of server-only imports (e.g., fs, process.env) so they can safely run on both sides.
Section 04

Technical Insights

Five non-obvious implementation details where the "obvious" approach would introduce real bugs, security gaps, or poor UX — and what the correct pattern looks like.

Security

Affiliate partner IDs must never reach the browser

The obvious implementation — embedding the full affiliate URL in the product card's href — exposes your partner tag in the page source. Any user can open DevTools, copy the tag, and use it in their own links, stealing your commission attribution. Worse, if you ever rotate the partner ID, every client-rendered page with the old URL is broken until users reload.

Correct pattern: The client renders /api/click?sku=sofa-002&option=B. The route handler owns the affiliate URL construction using an environment variable. Partner ID rotation is one env change + redeploy, with zero impact on any client-side code.

// ❌ Wrong — affiliate tag in client bundle
<a href="https://amazon.com/dp/B09XYZ?tag=dwelliq-20">Buy</a>

// ✓ Correct — only the SKU travels to the browser
<a href="/api/click?sku=sofa-002&option=B">Buy</a>

// Server-side (env var — never in bundle)
const tag = process.env.AFFILIATE_TAG // "dwelliq-20"
Browser Rendering

Three.js canvas must be dynamically imported to avoid SSR crashes

Next.js App Router server-renders pages on Node.js, which has no window, document, or WebGLRenderingContext. Importing Three.js at the module level causes an immediate crash during server rendering because Three.js accesses window at import time in some internal paths.

Correct pattern: Use Next.js dynamic() with ssr: false to defer the Three.js import to the client. This also avoids adding Three.js to the SSR bundle (a meaningful size saving on the server render pass).

// ❌ Wrong — Three.js at module level crashes SSR
import { HeroCanvas } from './HeroCanvas'

// ✓ Correct — deferred to client only
import dynamic from 'next/dynamic'
const HeroCanvas = dynamic(
  () => import('./HeroCanvas'),
  { ssr: false, loading: () => <div className="hero-placeholder" /> }
)
Data Modeling

sessionStorage is synchronous and can throw — always wrap it

In Safari's private browsing mode (and in some enterprise browser policies), sessionStorage is either disabled or throws a SecurityError on access. The obvious pattern — reading or writing sessionStorage directly in a component — throws an uncaught exception that crashes the entire React tree.

Correct pattern: Wrap all sessionStorage access in a try/catch utility. On failure, fall back to a module-level variable that survives re-renders but not tab closes — functionally equivalent for the session, with zero crash risk.

// ❌ Wrong — throws in private browsing
sessionStorage.setItem('dwelliq_onboarding_v1', JSON.stringify(data))

// ✓ Correct — graceful fallback
let memoryFallback: OnboardingContext | null = null

function saveOnboarding(data: OnboardingContext) {
  try {
    sessionStorage.setItem('dwelliq_onboarding_v1', JSON.stringify(data))
  } catch {
    memoryFallback = data // silent fallback — works for session duration
  }
}
UX Engineering

Budget tracker must debounce or batch — not recompute on every keystroke

If the budget input field triggers a full re-computation of all recommendations on every keystroke (300ms debounce is the obvious number to reach for), the user sees the A/B/C grid flickering with every character they type. The issue is that recommendations.ts, while fast at <5ms, causes React to re-render the entire results grid on each state update.

Correct pattern: Separate the "input" state from the "committed" state. The input field updates local state on every keystroke (instant, no recompute). The recommendation engine only runs on blur or when the user explicitly submits the budget — not on change.

// ❌ Wrong — rerenders full grid on every keystroke
<input onChange={e => setBudgetAndRecompute(e.target.value)} />

// ✓ Correct — commit on blur/submit only
const [inputValue, setInputValue] = useState(budget)
const [committedBudget, setCommittedBudget] = useState(budget)

<input
  value={inputValue}
  onChange={e => setInputValue(e.target.value)}
  onBlur={() => setCommittedBudget(Number(inputValue))}
/>
// useEffect on committedBudget triggers recompute
Security

The /api/click handler must validate the SKU — never reflect unvalidated input into a redirect URL

An open redirect vulnerability occurs when a server-side redirect uses unvalidated user input in the destination URL. In the /api/click handler, if you naively construct the affiliate URL by concatenating the user-supplied sku parameter into an Amazon URL, an attacker can craft a URL like /api/click?sku=../../../../evil.com and use your server as an open redirector for phishing attacks.

Correct pattern: Look up the SKU in the server-side catalog reference (an allowlist). If the SKU is not found, return 400. Never construct the redirect URL from user input directly — only from values that exist in your catalog.

// ❌ Wrong — open redirect via unsanitized sku
const url = `https://amazon.com/dp/${req.query.sku}?tag=${tag}`
return Response.redirect(url) // attacker controls destination

// ✓ Correct — lookup from allowlist (server-side catalog)
const product = CATALOG.find(p => p.id === req.query.sku)
if (!product) return new Response('Not found', { status: 400 })
return Response.redirect(buildAffiliateUrl(product.baseUrl, tag), 302)

Risk Register

Concrete risks across security, reliability, cost, and UX — with mitigations that either already exist in the current design or should be implemented before a public launch.
